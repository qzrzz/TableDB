# 文档 | Doc

TableDB 是文档数据库，简单来说你可以把任何 JavaScript 对象存储进数据库，而这时这个对象就被称为 “文档”（Document）。一个文档相当于是关系数据库中的一行（row），之所以叫文档而不是行，是因为它不需要遵循预先定义好的模式（Schema），每个文档都可以有任意的内容和结构，它只是一个普通的 JavaScript 对象。

```ts
table.insertOne({
    id: "my-doc-001", // 必须有唯一的 id 字段
    name: "Hello World",
    createdAt: new Date(), // 可以存储 Date 这样 JSON 不支持的类型
    metadata: {
        size: 991112312311211100n, // 也可以存储 bigint 类型
    },
    file: blob, // 可以直接存储 Blob，或者 Unit8Array 等二进制数据
})
```

除了必须有 `id` 和内部保留的 `_id` 字段以外，文档可以是任意结构，但是循环引用的对象是不行。

> [!NOTE] 文档大小限制
> 每个文档的大小取决于数据库实现，理论上 SQLite 支持最大 1GB，而 MongoDB 支持最大 16MB。

## 数据类型

TableDB 尽可能的支持所有 JavaScript 原生数据类型作为文档字段的值，
对于支持的类型，TableDB 会保证存储和读取时数据类型不变。

-   `string`, `number`, `boolean`, `null`, `undefined`
-   `Date`, `RegExp`, `Error`
-   `Map`, `Set`
-   `bigint`
-   `Blob`, `File`
-   `ArrayBuffer`,`DataView`
-   `Int8Array`, `Int16Array`, `Int32Array`,`Uint8Array`, `Uint8ClampedArray`, `Uint16Array`,`Uint32Array`, `Float32Array`, `Float64Array`, `BigInt64Array`, `BigUint64Array`

## 文档 ID

每个文档必须有一个唯一的 ID 字段，它会在各种操作中作为文档的唯一性标识符，理论上可以使用任意类型作为 ID 字段，但推荐使用 `string` 类型。

### 如何选择 ID 类型

理论上，一个完美的 ID 应该像 MongoDB 原生的 ObjectId 或者 UUID 那样，是个看来酷酷的二进制。
教科书会告诉你，这样省空间，效率高。但在现实的应用里，二进制这种东西，可不好相处。

你经常会陷入一种困惑：手里拿到的这个 ID，到底是二进制，还是已经被序列化后的文本？

虽然我们可以在 TableDB 里用 Schema 把这些脏活累活都藏起来，假装它们不存在，写代码的时候仿佛一切都很美好。
但当你半夜爬起来调试，盯着日志发呆，或者在运维时打开的 MongoDB Compass 中捣鼓数据时，你就会发现，
为了那一点点所谓的“理论优势”，你需要不断地手动转换格式。这不仅增加了工作量，还增加了你对这个世界的怀疑，尤其是你并没有拿到作为 DBA 的薪水。

所以，尽管 TableDB 宽容地支持所有类型（包括二进制）作为 ID，但我还是建议你：对自己好一点，**直接用字符串吧**。

在这个看脸的世界里，**可读性**有时候比那一点点微不足道的性能更重要。

所以虽然 TableDB 支持任意类型（包括二进制）的 ID，但**推荐直接使用字符串作为 ID 类型**，来获得更好的可读性和易用性。

**不同数据类型 ID 的性能对比**

或许你还是不信，没关系，我们来做个测试。 我们用 TableDB 分别测试了以下几种 ID 类型的性能：

> 总文档数: 1,000,000; 批量大小: 10,000; 查询次数: 1,000

| ID 类型            | 查询 (ms) | 查询 % | 插入 (ms) | 数据 (MB) | 索引 (MB) |
| ------------------ | --------: | -----: | --------: | --------: | --------: |
| `uuidv7_bin`       |       176 |    Ref |      2076 |     64.74 |     13.81 |
| `objectId`         |       177 |  +0.6% |      1939 |     56.16 |      9.12 |
| `uuidv7_short_str` |       183 |  +4.0% |      2323 |     69.51 |     16.09 |
| `uuidv7_str`       |       227 | +29.0% |      2081 |     83.82 |     21.37 |
| `uuidv4_short_str` |       247 | +40.3% |      7318 |     70.44 |     33.53 |
| `uuidv4_bin`       |       253 | +43.8% |     11611 |     64.74 |     26.26 |
| `uuidv4_str`       |       267 | +51.7% |     14789 |     83.82 |     86.60 |

从测试中可以看出，`uuidv4_bin` 和 `uuidv4_str` 的差异很小，说明使用字符串作为 ID 并不会带来明显的性能损失。

真正决定性能的，不是是否按二进制存储，而是它是有规律——也就是**有序性**。

`ObjectId` 和 `UUIDv7` 都是有序的 ID，所以性能更优，而 `UUIDv4` 是完全随机的 ID，所以性能较差。

另外使用 Base58 编码的 `uuidv7_short_str`, `uuidv4_short_str` 相比标椎的 hex 编码的 UUID 字符串，性能也有一定提升，
用更短的字符串表示同样的 ID，实在是太棒了，减少了存储大小，提升了查询性能，用户体验也更好（URL 会短一点）
。

所以最终的文档 ID 推荐建议：🏆 `UUIDv7 Short`

使用 Base58 编码的 UUIDv7 字符串，只要你场景不需要隐藏 ID 创建时间，就是最推荐的 ID 格式。

> [!IMPORTANT] 隐私注意
> 但凡事都有代价。UUIDv7 是诚实的，它按时间顺序生成，所以它会把创建时间写在脸上。有心的人可以据此推算出你究竟有多少文档，看穿你的产品增长曲线。
>
> 如果你需要绝对的隐私，不想让任何人窥探你的底牌，那你就必须放弃有序性带来的红利，去选择 UUIDv4 Short。虽然它性能稍微差一点，但它守口如瓶。在这个世界上，想要安全，有时候就得牺牲一点速度。
